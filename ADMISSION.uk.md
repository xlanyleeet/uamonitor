# Заявки та Discord-модерація

Працює в копії `uamonitor-go`. Публічна адреса для конфігурації: `https://monitoring.gradient-mc.com`.

## Підключення

1. Створіть incoming webhook у **приватному** каналі модераторів Discord.
2. У локальному `.env` задайте `UM_DISCORD_WEBHOOK_URL=https://discord.com/api/webhooks/.../...` та `UM_PUBLIC_URL=https://monitoring.gradient-mc.com`.
3. Запустіть `docker compose -p uamonitor-go up -d --build --wait`. Міграції застосовуються сервісом `migrate` перед backend.
   Для вже запущеного proxy після зміни `deploy/nginx.conf` виконайте `docker compose -p uamonitor-go exec -T proxy nginx -t`, потім `docker compose -p uamonitor-go exec -T proxy nginx -s reload`.
4. Сайт має відкриватися за цією HTTPS-адресою. DNS, TLS і зовнішній reverse proxy налаштовуються окремо. Локальний stack слухає тільки `127.0.0.1:9013`; для зовнішнього reverse proxy збережіть заголовок Origin браузера. API перевіряє його за `UM_PUBLIC_URL`.

Без webhook форма доступна для перегляду, але надсилання вимкнено; API повертає 503. Наявність webhook у конфігурації не гарантує його чинність: перевірте тестовою заявкою після підключення. Не вставляйте webhook у frontend, Git або публічний канал.

## Процес

- POST `/api/applications`: серверна перевірка полів, згода з вимогами, обмеження тіла 20 KiB, до трьох збережених заявок з однієї адреси за годину і до 30 загалом за годину. Є також ліміт запитів proxy/API. Це базовий захист; для відкритого інтернету за потреби додайте challenge на зовнішньому proxy.
- Повтор надсилання з тим самим випадковим `Idempotency-Key` повертає ту саму квитанцію. Інший вміст із тим самим ключем відхиляється. Дублікати адреси в каталозі та серед заявок на розгляді відхиляються.
- PostgreSQL зберігає повну заявку, приватні контакти та стан доставки. Backend перевіряє чергу кожні 15 секунд. Після збою — повтор зі збільшенням інтервалу до 512 хвилин, у тому числі після перезапуску. `wait=true` дозволяє перевірити відповідь Discord.
- Discord отримує назву, адресу, опис, версії, режими й контакт представника та дві link-кнопки. Усі інші відповіді доступні на приватній сторінці. Mentions вимкнені.
- Link-кнопки відкривають `/moderation/{id}`. GET нічого не змінює. Остаточне рішення — POST із CSRF cookie, токеном і перевіркою Origin. Відмова потребує причини. Додавання сервера та рішення зберігаються в одній транзакції; повторне рішення не створює дубль.
- Після схвалення сервер з’являється в каталозі; перший ping виконає черговий цикл моніторингу (типово до 10 хвилин). Контакт представника не потрапляє в публічне API. Правила, режими та інші відповіді залишаються в заявці; публікуються назва, адреса, опис і вебсайт.
- Власник бачить номер, контакт для відповіді та приватне посилання `/applications/{id}#ключ`. Воно показує стан, пояснення рішення й посилання на схвалений сервер. Ключ надсилається в Authorization, не в URL запиту API, і не дає права модерації. Зберігайте повне посилання разом із фрагментом після `#`. Старі заявки без збереженого ключа не отримують нового доступу автоматично.
- Чернетка відновлюється після оновлення тієї самої вкладки протягом доби. Вона зберігається в sessionStorage, містить введений контакт і видаляється після успішного надсилання. Підтвердження повноважень і згоди потрібно поставити знову. Автоматичні email/Discord DM не надсилаються; модератор відповідає через наданий контакт.

## Межі доступу

Звичайний incoming webhook підтримує link-кнопки через `with_components=true`; інтерактивні `custom_id`-кнопки потребують Discord application та endpoint для interactions. Тут підтвердження відбувається на сайті. Див. [Discord webhooks](https://docs.discord.com/developers/resources/webhook) та [buttons](https://docs.discord.com/developers/components/reference).

Приватне посилання — право ухвалити рішення, без Discord OAuth та перевірки ролей. **Кожен, хто має посилання, може модерувати відповідну заявку.** Тому канал має бути приватним; посилання не пересилайте. Воно діє 30 днів. У БД зберігається токен для повторного надсилання; захищайте доступ до БД і резервних копій. Nginx не записує URL `/moderation/` в access log; сторінка забороняє кешування, referrer та iframe. На зовнішньому proxy також вимкніть журналювання query string для цього шляху.

Доставка Discord — at least once: якщо Discord прийняв повідомлення, але відповідь загубилася, можливий повтор повідомлення. Транзакційне рішення залишається одноразовим. Наразі Discord-повідомлення після рішення не редагується; актуальний стан видно на сторінці перевірки. Аудит зберігає рішення, причину й час, але не ідентифікує Discord-акаунт модератора.

Заявки та рішення зберігаються без автоматичного видалення. Перед публічним запуском визначте строк зберігання контактів і процедуру їх видалення. Зміни нижче перевірені без надсилання в реальний Discord: Go-тести використовують підмінений HTTP transport та окрему тимчасову PostgreSQL-схему.
